# WebView 键盘许可：按触摸落点判定，而非是否发生过触摸

> 适用环境：Android WebView 外壳（SDK 35 一档），真机实测，坐标为页面 CSS px。

## 现象

点左侧侧栏里的会话进入对话，输入法键盘区被拉起；点输入框时拉起才是正确行为。

## 根因（与直觉相反）

上一版判据是「这段时间里有没有触摸事件」。点会话同样产生触摸，于是误发键盘许可，页面紧接着自动聚焦输入框，键盘区照样被拉起。**触摸存在 ≠ 输入框被点。**

## 正确判据：落点是否真的在输入框上，且是最顶层

- 只做矩形包含判断不够。点会话时手指坐标 (126,533) 恰好落在下层输入框矩形内（输入框 x 16~366、y 484~536），因为侧栏浮在其上，矩形判断会把会话点击判成输入框触摸。
- 必须用 `document.elementFromPoint(x, y)` 取该点的**最顶层**元素，再判断它是否属于输入框（或输入框子节点）。有浮层时这是唯一可靠判据。

## 坐标来源要挑准

- 同一手势实测：`touchstart` 坐标 (0,0)，`pointerdown` 坐标 (193,825)。合成触摸的 touch 坐标是 0,0，拿去 `elementFromPoint` 只会命中左上角元素，判定必然错。
- 优先采信 pointer/mouse 坐标；touch 坐标仅在确认非 (0,0) 且可信时使用。

## 兜底必须轮询，不能只查一次

- `onPageFinished` 后 250ms 查一次太早：页面聚焦输入框的时机在 0.3~0.8 秒之间浮动。
- 改成 0.2 / 0.5 / 0.9 / 1.4 秒各查一次；命中后一并复位 `#root` 高度与 `--dsh-native-keyboard`，避免残留键盘区。

## 验证数据（真机）

| 场景 | 结果 |
|---|---|
| 点侧栏会话 | `rootH=895`、`kb` 空、`active` 空、`mInputShown=false` → 无键盘区，会话正常进入 |
| 点输入框 | `rootH=574`、`kb=321px`、`hit={193,825}`、`mInputShown=true` → 键盘正常拉起 |
| 冷启动 | 干净，无键盘区 |
| 单测 | 22 个全部通过 |

## 附带踩坑：不要用哈希类名定位

曾把 `.an3WzG_scrollBody` 当成侧栏，实际那是主界面滚动容器；侧栏是 `.wtg9ga_*` 那一套，收起时整体平移到 `x=-207`。哈希类名随构建变化，不能当长期判据，定位要用结构/语义标记。
