# 外部依赖的隐式契约：把「会静默失效的耦合点」写成可检查的文档

> 适用环境：WebView 外壳类 App（App 依赖某个不受你控制的服务 / 中间层 / 私有协议），也可推广到任何「依赖对方内部实现细节」的项目。
> 最后验证：2026-11，dsh-mobile-app 对照 dsh-pocket 2.12.0。

## 问题：最贵的缺陷是「对方一升级就静默失效」的那种

WebView 外壳的代码量很小（本项目 Kotlin 不到两千行），但它的正确性压在别人的实现细节上。这类耦合错在没有编译期检查、没有运行时断言，**升级对方就悄悄坏掉，而你的代码一行没改**。

本项目实际依赖的外部细节（全部是实测出来的，不是看文档抄的）：

| 耦合点 | 具体形态 | 失效后果 |
|---|---|---|
| cookie 名 | `dsh_pocket_token` | 清错 cookie → 要么自愈无效，要么把用户永久锁在验证页 |
| cookie 值的构造 | `sha256(PIN + ":" + sessionKey)`，`sessionKey` 是 dsh web 进程级随机数 | 对方的寿命语义变了，你的「长期免输」承诺就不成立 |
| 中间件「已有 cookie 就不再下发」 | `maybeSeedAuthCookie` 第一行 `return` | 残留一个坏 cookie 就永远拿不到新的 |
| 认证 URL 形态 | `?token=<PIN>`，token 会被消费掉 | 重连时用错了 URL 就进不去 |
| 重试参数 | `dsh-pocket-retry=1`，且必须插在 `#` 之前、限流 3 次/60s | 拼错位置 → 参数落进 fragment，服务端收不到 → 撞 503 |
| 页面文案 | `受访问密码保护` / `无法完成登录握手` / `探索未至之境` 等 | 判据静默失效 → 自愈要么不触发，要么误删 cookie |
| 地址不落盘 | 隧道 URL 每次重启都变，本地只有 `{"at":<ts>}` | 用户重开 App 就找不到入口 |

## 决策：为耦合面单独写一份 INTEGRATION.md，并把检查写成可执行命令

不写「注意事项」散落在代码注释里——那等于没写。单独一份 `INTEGRATION.md`，每个耦合点必须包含四栏：

1. **对方的实现位置**（文件 + 行号，例如 `proxy.mjs:509-525`）；
2. **我方依赖的具体行为**（一句话，写成可验证的断言）；
3. **失效的可见症状**（用户看到什么，而不是日志说什么）；
4. **升级后的检查命令**（能直接复制运行的 grep / curl / CDP 片段）。

第 4 栏是关键。没有它，文档在半年后就是一段「看不懂当时在说什么」的散文。

### 配套的三条做法

- **升级对照表**：文档顶部钉死「对照版本 dsh-pocket 2.12.0」。对方升版就重跑一遍第 4 栏的命令。
- **明确写「我不依赖什么」**：这一节价值不亚于依赖清单。本项目明确不依赖 dsh web 的端口、不依赖中间层的 RPC（`pocket.status` / `tunnel.start`）、不依赖对方的设置文件格式——这些都在变，能不用就不用，少一个耦合点就少一处静默失效。
- **未验证的事写「未验证」**：踩过一个坑，把「疑似原因」当成结论写进注释，后来证伪。凡是没抓到证据的机制，文档里必须标注为推测；否则下一个人会基于错误结论做出更贵的改动（本项目就因此追查过一个不存在的导航缺陷）。

## 什么时候该抽接口 / 什么时候不该

判据是「**这个决策判错时会造成不可逆损害吗**」：

- 会 → 抽成纯 JVM 类 + 接口注入副作用，用单测覆盖所有分支。本项目的 `RecoveryPlanner`（决策）、`HandshakeHealGate`（计数）、`PageProbe`（判据）都是这样，因为这些判错会删用户的 cookie。
- 不会 → 不要为了「架构好看」抽。UI 构造、`CookieManager` 调用、`WebView` 生命周期这些留在 Activity 里完全可以，抽出去只会多一层。

反过来说：**测试覆盖率的意义不是「覆盖率百分比」，而是「判错会伤到用户的那几行有没有被覆盖」**。本项目 118 个单测全部集中在这几个纯逻辑类上，UI 层一个都没有——这是刻意的取舍，不是遗漏。

## 一次判据失配的真实代价（为什么值得花时间做这件事）

`PageProbe.classify` 的判据顺序错一次（把「访问密码」判在「探索未至之境」之前），后果是：正常主界面的设置页正文里含有「访问密码」字样 → 被判成「要 PIN」→ 触发清 `dsh_pocket_token`。而清理之后如果 URL 里的 token 已被消费掉，用户就**再也进不去了**。

这类错误无法用真机试错覆盖（要试的组合太多，且失败现场恢复成本高）。所以判据必须能在 JVM 里用字符串测完——这就是「判据拆两半」那套设计的全部理由。
